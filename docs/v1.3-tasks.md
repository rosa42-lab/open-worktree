**目标版本：** `orch 1.3.0-candidate`（建议）  
**基线：** `1.2.0-candidate`（本地 merge queue / Agent runtime / Topic 已落地）  
**阶段数：** 6（Phase 0 / 1 / 1.5 / 2 / 3 / 4，对齐设计 §17）  
**状态：** Phase 0–3 **代码已落地**（含 V13-009～011）；M3a/M3b/M3c 夹具 E2E 通过；版本 `1.3.0-candidate`；下一步 **V13-012 人工签署**（ready checklist D 门）；`candidate_pr` 全路径仍 defer

本文将现行设计的目标、架构决策、CLI、数据模型、失败恢复与验收标准拆成可独立验收的开发任务。每个阶段必须满足退出条件后才能进入下一阶段；Phase 2/3 以 Phase 1.5 为硬门槛。

## 1. 全局约束

- Python 核心仅使用标准库，不引入第三方 Python runtime dependency。
- 固定晋级链：`feature/* → local develop → origin/develop → develop→master Promotion PR → origin/master → release-sync → release tag`。
- `integration_branch` 初始必须是 `develop`；`stable_branch` 初始必须是 `master`；`release_merge_method` 初始必须是 `merge_commit`。
- 本地 merge queue（`tasks` 状态机）与远端 `promotion_runs` 状态机分离；正常 feature 变更只由 merge queue 产生。
- master/candidate merge commit 纳入 local develop **只能**走受锁、可审计的系统 ref 同步：`release-sync` 或 `promotion-reconcile` 的 candidate-sync；不得伪装成普通 feature task。
- origin/develop 写入必须带显式 `expected_old_sha`/`new_sha` 的非强制 CAS；禁止 `--force` 与 `--force-with-lease`。
- origin/master 不得由 orch 直接 push；只通过同仓库 `head=develop`、`base=master` 的 Promotion PR，且必须 merge commit。
- 发布窗口默认同时冻结：`promote-develop` **与** local develop merge queue（`freeze_develop_during_release` / `freeze_local_merge_queue_during_release` 初始均为 `true`）；feature worktree 仍可开发与入队。
- 平台报告 master 已合并后不得直接标 `released`；必须完成 `release-sync` 且 remote develop == `release_merge_sha`。
- 所有 Git 子进程仅经 `orch.git` / `orch.remote.git`：argv、`shell=False`、超时；不得依赖 checkout 或 `push.default`。
- 网络、Git、provider API 不得放入长 DB 事务；secret 不得进入 argv、SQLite、audit、JSON、异常或 remote URL。
- `unknown` / 无法证明必须 fail-closed（`blocked` / `manual_required` / `reconciling`）。
- 不破坏现有 v1.1/v1.2 语义与回归；领域服务只依赖 Protocol，不散落 GitHub JSON。
- Phase 0 致命假设失败时先更新架构决策（`direct_ff` / `candidate_pr` / `blocked`），不得带着未验证假设进入写路径。
- **Solo 例外（非设计默认）：** master Ruleset 可临时允许 `OrganizationAdmin` bypass 以打破「唯一 Code Owner = PR 作者」死锁；团队化后必须移除。详见 `docs/github-app-ruleset-setup.md` §8。不得把个人管理员 bypass 当作常态。

### 阶段 0：GitHub 能力探测与人工 Ruleset 落地

**目标：** 关闭设计 §16 **致命**假设（develop/master 写边界、禁 force、mode 冻结）；merge-commit 父提交证据可来自真实 Promotion PR；**远端 `release-sync` FF 演练归 Phase 3 / V13-011**（本地图前提见设计 §16.1）。

#### V13-001：GitHub Capability Probe 与 Ruleset / 能力证据

- **优先级：** P0
- **依赖：** 无
- **设计锚点：** §5、§6、§8.2、§12.4、§16、§16.1、§17 Phase 0
- **任务：**
  - 创建或确定 Integration / Release GitHub App（可临时合并，仍禁止 master direct push 与 approval）。
  - 人工配置 develop/master Ruleset（§6.1–§6.2）；master **必须** merge commit，禁止 squash/rebase 作为正常模式。
  - 落地 `promotion-policy` workflow（§6.3）为 master required check。
  - `remote-probe` 只读原型：不改分支；输出 `verified` / `unsupported` / `unknown` / `misconfigured`；**显式验证** `refs/heads/develop` 与 `refs/heads/master` 存在，不得用 default branch（如 `main`）推断 `stable_branch`。
  - 原型即须覆盖设计 §8.2 检查表全部分类（可标记部分为 `unknown`，但不得省略类别）：
    - **Git**：remote 可达、develop/master 存在、默认 fetch 行为；
    - **身份**：当前 Bot 身份、可见仓库与权限范围；
    - **develop policy**：禁止 force/delete、仅 Integration Bot 可写；
    - **master policy**：PR-only、审批、checks、stale approval、no bypass；
    - **provider**：创建/查询 PR、读取 checks/reviews、读取 branch protection。
  - 演练并落盘脱敏证据：
    - Integration App 可更新 develop、不可 push master；
    - 个人/Agent 不可直接 push 核心分支；
    - **(a) Phase 0：** master Promotion PR 的 merge commit 保留 develop source 父提交（真实 PR 证据即可，如 PR #1）；
    - **(b) Phase 3 / V13-011：** 远端 `release-sync --execute` 将该 merge commit FF 回 origin/develop（**非** Phase 0 硬退出）；
    - 错误来源 PR / stale approval：**方案 §17 允许延后到 Phase 3**；合约证据归 **V13-009 + V13-012**（方案 §16 表仍标「致命/高」，以 §17 Phase 0 退出口径为准，见 matrix 对照）；
    - 非 force push 在 expected old SHA 不匹配时被服务端拒绝（CAS 竞态；可延后到 orch CAS / V13-009）；
    - Bot 凭证不出现在 argv/log（含 askpass / credential helper 路径，对齐 §5）。
  - 若 provider 无法提供非 force 的旧/新 SHA CAS → probe 标 `unsupported`，只能走 `candidate_pr` 或 `blocked`。
  - 固定模式：`direct_ff` | `candidate_pr` | `blocked`；致命假设失败则先改设计决策。
- **交付物：**
  - `docs/probe/v13-phase0-capability-matrix.md`（按 §8.2 五类检查列矩阵）
  - 脱敏证据（ruleset、正反 push、merge-commit 父提交；远端 release-sync 演练归 V13-011）
  - `promotion-policy` workflow
  - `remote-probe` 只读入口（可最小，但五类检查均有输出槽位）
- **完成定义：** §16 写边界/禁 force/mode/refs/merge-commit **父提交**有真实结论（对齐 §17 Phase 0 退出）；§8.2 五类均有结论行；模式写入矩阵；`unknown` 不作通过。
- **自动化状态：** 人工 + Runtime 证据 **PASS**（2026-08-01）；CLI `remote-probe` 仍为 Phase 0 原型（provider 槽位多为 `unknown`），完整自动化归 **V13-009**。本地 Git 图前提见设计 §16.1。
