## V13-009：HostingProviderAdapter 与 GitHub 实现

**父任务 DoD：** PromotionService 无直接 GitHub HTTP；§8.2 五类检查可自动或明确 `unsupported`/`misconfigured`；权限不足 ≠ `verified`。

### V13-009-1 — HTTP 客户端与凭证边界

- **任务**
  - `orch/remote/http.py`（或 `github_http.py`）：stdlib `urllib`；超时；`Authorization` 永不进日志/异常/`details`。
  - 凭证来源：环境变量 / 内存 token（installation token）；禁止拼进 remote URL、argv。
  - 统一错误映射：401/403/404/422/429/5xx/超时 → 稳定 `kind`。
- **交付物：** HTTP 封装 + 脱敏单测  
- **验收：** 伪造响应含 token 时审计/JSON 无明文 secret  

### V13-009-2 — 领域字段契约

- **任务**
  - 固定 Provider 返回结构（文档化摘录）：
    - `probe_capabilities` → `{ok, checks[], identity, permissions_summary}`
    - `branch_policy(branch)` → `{exists, allow_force, allow_delete, require_pr, required_checks[], bypass_summary, merge_methods[]}`
    - `create_promotion_pr` / `get_pr` → `{external_id, url, head, base, head_sha, base_sha, state, merged, merge_commit_sha, mergeable, mergeable_state}`
    - `get_checks(external_id, source_sha)` → 仅统计 **绑定该 SHA** 的 checks
    - `get_reviews(external_id, source_sha)` → 审批是否绑定该 SHA；bot 审批可标记但不满足 code owner
  - squash/rebase merge：`merge_method` 或 parents 检测失败 → `kind=merge_not_syncable`
- **交付物：** `docs/probe/v13-provider-field-contract.md`（短）+ 类型注释  
- **验收：** 合约测试只断言领域字段，不散落 raw GitHub JSON 到 service  

### V13-009-3 — `GitHubProviderAdapter` 实现

- **任务**
  - `orch/remote/github.py`：实现 Protocol 全部方法。
  - Ruleset/protection 读取：优先 REST rulesets；权限不足 → `unknown`/`misconfigured`，**不得**标 `verified`。
  - `mergeable is null`：有界退避（次数/总超时可配置常量）。
  - PR 幂等：同 head/base/title 已存在则复用。
- **交付物：** `github.py`  
- **验收：** 对 `rosa42-lab/open-worktree` 只读调用（status/PR list）可用 installation 或 `gh` 旁路测通至少一条  

### V13-009-4 — `manual.py` / `gitlab.py` 占位

- **任务**
  - `manual.py`：全部方法明确 `unsupported` 或人工粘贴结果路径（若需要）。
  - `gitlab.py`：`NotImplementedError` / `unsupported`。
- **验收：** import 与工厂选择不炸；默认 github  

### V13-009-5 — 升级 `remote-probe`

- **任务**
  - `orch/remote/probe.py`：在已有 Git 槽位上接入 provider：
    - 身份、develop policy、master policy、provider 能力
  - 输出仍为五类数组；每项 `verified|unsupported|unknown|misconfigured`
  - 汇总：`overall` 不得在任一致命项 `unknown` 时宣称可写 master/develop
  - 关闭 `docs/probe/v13-phase0-capability-matrix.md` pending：provider 行、CAS 竞态观测、stale approval（能读则填）
- **验收：** 无 token 时身份/policy 为 `unknown`/`misconfigured`；有 Release/Integration 只读 token 时可对真实仓得出非 unknown（至少部分）  

### V13-009-6 — Provider 合约测试（§18.3）

- **任务**
  - `tests/test_github_provider_contract.py`：mock HTTP
    - 401/403/404/429/5xx/超时
    - PR 幂等、head/base 校验
    - checks/reviews 绑 SHA
    - 外部关闭/修改/合并
    - merge commit vs squash 拒绝
  - 关闭 matrix **#10**：`promotion-policy` 拒非 develop→master（坏 head）；可选真实仓烟测
  - 关闭 matrix **#9**：bot 审批相关合约（能 mock 则 mock）
- **验收：** 无网络也可全绿；可选 `@integration` 标记真实仓烟测  

**V13-009 退出：** M3a；写路径仍不自动合并 master。

**完成记录（2026-08-01）：** 009-1…009-6 全部落地；合约测 PASS；matrix #9/#10 mock 关闭；真实仓 E2E 仍归 V13-012。

## V13-010：release-create / status、双冻结与 master 状态机

**父任务 DoD：** 错误来源/失败 CI/过期审批/移动 SHA 不能进 `released`；双冻结可测；不自动批准/合并。

### V13-010-1 — master_release 状态机

- **任务**
  - `orch/promotion/state.py`（或 `master_state.py`）：§10 合法转换表  
    `created → … → ready_to_merge → master_merged_pending_sync → syncing → released`  
    以及 `blocked` / `reconciling` / `manual_required` / `cancelled`
  - 非法转换单测
- **验收：** 与 develop 表分离；`released` 仅能从 syncing 成功进入（由 V13-011 调用）  

### V13-010-2 — release precheck（§10.1）

- **任务**
  - 全部前置（按设计 §10.1 写死，无开放问句）：
    1. origin/develop、origin/master 可确定且 refs 存在；
    2. origin/master 是 origin/develop 的祖先；
    3. **没有**其他 active `master_release`；
    4. 无 active `develop_publish`（非 succeeded/cancelled）；
    5. develop promotion 已成功且 `remote_develop_sha == local_develop_sha == source_sha`（建议硬约束）；
    6. aggregate verification 绑定当前 **remote develop tip**，未过期、required commands 成功；
    7. `release_merge_method=merge_commit`；master ruleset / policy check 已验证；
    8. PR source/base 必须同仓库 `develop`/`master`。
- **交付物：** `orch/promotion/release_precheck.py`  
- **验收：** 缺 verification / squash 仓配置 / 无 master ref / 存在 active promote 或 release → `blocked`  

### V13-010-3 — `release-create`

- **任务**
  - CLI：`orch <project> release-create --verification <id> [--title ...] [--json]`
  - 经 provider 创建 `head=develop, base=master` PR
  - 写入 `promotion_runs`：`kind=master_release`, `mode=promotion_pr`，external_id/url、source_sha、target_sha_before、verification_record_id
  - PR body metadata（无 secret）：`orch-promotion-id` / source-sha / …
  - **不** approve、**不** merge
- **验收：** dry 可预览；execute 创建 PR；重复调用幂等复用  

### V13-010-4 — `release-status`

- **任务**
  - CLI：`orch <project> release-status <promotion_id> [--json]`
  - 拉取 PR：head/base、head_sha vs 冻结 source_sha、checks、reviews、mergeability、master tip、是否被外部改 head/关 PR
  - checks/approvals **必须**映射冻结 SHA
  - 状态推进：仅观察态（如 awaiting_checks → ready_to_merge）；**检测到平台已 merge** → `master_merged_pending_sync`（仍非 `released`）
- **验收：** 移动 head / 失败 check / 缺审批 → 不可标 ready_to_merge；已 merge → pending_sync  

### V13-010-5 — 双冻结守卫（D5）

- **任务**
  - 存在 active `master_release`（非 succeeded/released/cancelled）时：
    - `promote-develop --execute` → 拒绝（precheck 已有雏形，补齐所有 active 态）
    - local `merge` / claim → 拒绝并说明 `release_freeze`
    - `enqueue` **允许**；feature worktree 提交允许
  - 接入 `orch/merge/claim.py` 或 `commands/merge.py`
- **验收：** 单测模拟 active release 时 merge/promote 失败、enqueue 成功  

### V13-010-6 — 禁止同 PR 滑移

- **任务**
  - status/reconcile 检测：head 变更、Update branch、base 变更 → `blocked`
  - 需要新代码时：cancel 当前 release → 重新 promote-develop → 新 release-create
- **验收：** 夹具模拟 head_sha 变化 → blocked  

**V13-010 退出：** M3b；合并后停在 `master_merged_pending_sync`。

**完成记录（2026-08-01）：** 010-1…010-6 落地；E2E 覆盖 create/status/slip/freeze。

## V13-011：release-sync、master reconcile、cancel（release）

**父任务 DoD：** 未 sync 不能 `released`、不能解除双冻结；sync 幂等可审计。

### V13-011-1 — `sync_verified_merge` 实现

- **任务**
  - 去掉硬拒；实现：证明 `source_sha → published_sha` 为 FF；更新 **local** develop（`--ff-only` / 等价 ref 更新）；可选再 CAS push origin/develop（由调用方编排）
  - 仅领域层（release-sync / 未来 candidate-sync）可调用
- **验收：** bare fixture：合法 FF 成功；非祖先失败；不 force  

### V13-011-2 — `release-sync` 命令（§8.7）

- **任务**
  - CLI：`orch <project> release-sync <id> [--execute] [--json]`
  - 仅接受 `kind=master_release` 且态 ∈ {`master_merged_pending_sync`,`syncing`,`reconciling`}
  - 步骤（锁内读、Git 在事务外）：
    1. fetch；校验 provider `merge_commit_sha` == master tip，且含 `source_sha` 祖先
    2. local develop ∈ {source_sha, merge_sha}
    3. dry-run：打印计划；`--execute`：local FF + events `release_sync_*` + CAS `origin/develop` expected_old→merge_sha
    4. 双 ref 复核后 → `released`；解除冻结
  - squash/ancestry 失败 → `blocked`/`manual_required`，禁止 `released`
- **验收：** 集成测覆盖成功路径 + 竞态 + 未 execute 不写  

### V13-011-3 — master `promotion-reconcile`

- **任务**
  - 扩展 reconcile：`kind=master_release` 时读 PR/master/develop tip，不盲推
  - 证据足够时可委托同一幂等 `release-sync` 核心函数
  - 超时/未知 → `reconciling`
- **验收：** develop 与 master 两条路径分派正确；candidate 仍 `unsupported`  

### V13-011-4 — master `promotion-cancel`

- **任务**（对齐方案 §8.8 + §10 状态图；**禁止**隐藏已发生的 master 写入）
  - **允许 cancel 的状态：** `created` / `blocked` / `manual_required`（与 §10 图一致）。
  - **禁止**从 `master_merged_pending_sync` / `syncing` / `released` 直接 cancel。
  - master **已合并**且 develop **未 sync** 时：必须走 `release-sync` 或 `promotion-reconcile`；证据不足/失败 → `manual_required`（记录观测 SHA）→ 再 `promotion-cancel --reason`（仍不得假装 master 无写入）。
  - 合法 cancel 后解除双冻结；取消后不得跳过 precheck 重用同一 source SHA 开新 release。
- **验收：** pending_sync / syncing 调 cancel → 拒绝；`manual_required` 取消有 actor/原因/观测 SHA 事件  

### V13-011-5 — 冻结与 `released` 耦合测试

- **任务**
  - 断言：`master_merged_pending_sync` / `syncing` 期间双冻结仍生效
  - 仅 `released` 或**合法** `cancelled`（来自 created/blocked/manual_required）后 promote/merge 恢复
- **验收：** 端到端夹具或状态机+守卫单测  

**V13-011 退出：** M3c；阶段 3 退出条件可勾选。

**完成记录（2026-08-01）：** 011-1…011-5 落地；`test_release_e2e_v13` full sync → released。
